# Weekly-report source retries and diagnostics

Date: 2026-09-28

## Behavior

Scheduled and manual bulk jobs share the same source client. Each read-only
source page now receives at most three attempts. Timeouts, network errors,
HTTP 408/429 and HTTP 5xx retry after 2 and 4 seconds. Other HTTP errors,
invalid JSON and invalid response contracts fail immediately. The exact page
request is reused; staging starts only after a validated response. Completed
pages/items are not regenerated by a source retry.

`WEEKLY_REPORT_SOURCE_TIMEOUT_SECONDS` remains 30 by default, now validated as
finite and greater than zero through 120 seconds. It also bounds the entire
HTTP attempt, preventing slow responses from extending the request indefinitely.
The default exhausted page takes at most approximately 96 seconds of HTTP and
backoff time (366 seconds at the maximum), below the default 900-second producer
lease. Custom shorter producer leases must exceed this retry budget plus staging
time. Async task cancellation propagates through requests and backoff.

Exhausted retries still terminate the job. This change does not reset already
failed jobs, add cron catch-up, retry production migration, or replace the stable
weekly idempotency key. Source retries apply to the interactive client as well.

## Diagnostics

The worker writes one JSON object per log line, with UTC timestamp, level,
logger/event, and allowlisted metadata. Existing job admission, completion and
failure records now retain their job ID, stage, counters and error code.
Source events are `weekly_report_source_started`, `weekly_report_source_retry`,
`weekly_report_source_completed` and `weekly_report_source_failed`.

Source events include job ID for bulk execution, reporting week, attempt/maximum
attempts, timeout, elapsed seconds, retry delay, exception type and HTTP status
when applicable. Terminal producer failures include the source error code,
underlying exception type and exhausted attempt count. Exceptions are logged by
type, without raw messages, tracebacks, request URLs, credentials, response bodies,
ward names, source snapshots or generated report text. These diagnostics are
container logs, not new fields in the persisted job/API contract.

Scheduler JSON events now include a timestamp. A failed generation poll emits
`weekly_report_schedule_job_failed` with job ID, reporting week, status,
discovered/completed/failed counts and producer completion before the existing
pipeline failure event. Use its job ID to correlate worker/source errors.

## Rollout

From the parent `nexgent` directory, after active generation has finished:

```bash
sudo docker compose -f compose.prod.yaml up -d --build --no-deps weekly-report-worker weekly-report-scheduler
```

Rebuilding Agent Server separately adopts the same source retries for the backend
interactive compatibility graph. No database migration or environment change is
required for defaults. Rebuilding does not repair the already-failed September 21
job or migrate a manually generated replacement. Check that replacement's terminal
status and follow the existing production migration procedure independently.

failures, invalid JSON/contracts, cancellation during requests/backoff, whole-attempt

Live deployment and production recovery remain operator steps.
